# Offline Login Revival

一套从"只有一个客户端"到"登录完整跑通并可持续迭代"的通用方法论，适用于已关服 / 服务不可达的联网客户端（游戏、App）。

一句话本质：**客户端本身不包含运行所需的全部逻辑，缺失的那部分在服务端。所谓"复活"，就是把缺失的服务端逻辑依据客户端留下的线索补回来。** 优先目标是先跑通登录——登录跑通就意味着客户端已连上自制服务端，项目成功了一半。

> 适用范围：仅供游戏开发的学习与研究。请勿用于仍在运营的游戏，或用于绕过合法授权 / 付费。加密加壳、特殊架构等不在本方法论覆盖范围内，需对具体游戏具体分析。

## 何时使用

- 客户端能启动，但卡在登录 / 连不上服务器 / 提示网络错误；
- 服务已下线，但有可运行的客户端与可观测的脚本 / 字节码；
- 需要为私服、离线复原、协议研究搭建本地服务端；
- 需要在多版本客户端之间复用同一套逻辑。

不要在以下场景硬套：客户端已被完全加密且无任何可观测点；目标是绕过合法授权 / 付费墙。

## 第一步：战略选型（先决定"补哪一边"）

在写任何代码前，先选总体路线。三条路线的取舍：

| | 复原服务端（推荐通用解） | 改造客户端 | 重做客户端 |
|---|---|---|---|
| 思路 | 重写一个能配套运行的服务端，让客户端"以为"仍在官方服务器上 | 注入代码，把原本发给服务端的请求在客户端内部处理，单机化 | 只提取资源（模型/动画/场景），重做展示工具 |
| 优点 | 通用性最强；可保留多人功能；对客户端改动最少、与原逻辑兼容度最高 | 无需运行服务端；启动简单；有机会做成点开即玩的单机版 | 难度最低；可只保留角色/演出；不依赖原协议 |
| 缺点 | 启动链复杂（代理+注入+服务端）；服务端未必能跑在手机上；协议与逻辑需逐步补齐，工作量大 | 需深入改已编译代码，受引擎/混淆/平台影响大；服务端独有规则与数据可能无法恢复 | 无法保留完整玩法与联机；想还原全部内容≈重做一款游戏 |
| 适合 | 大多数场景（默认选它） | 客户端代码相对易读易改（如 Cocos/TS→JS） | 只想要角色、剧情、场景展示 |

**默认选择"复原服务端"**，本方法论其余部分均围绕它展开。两条子工作线：
- **流量重定向**：用 TLS 代理 + 静态/动态注入，把请求与写死的地址改到本地服务端（静态注入=改文件，动态注入=改内存）；
- **数据应答**：自制服务端接收请求并回传符合协议的数据。

## 第二步：前提与线索（静态分析优先）

**先不运行游戏**，从文件与代码里能挖出多少就挖多少。开动前的硬前提与三类线索：

### 前提：客户端文件是否齐全？

手游安装包常只含一部分，其余靠**热更新**下载；关服后若本地没有留存，轻则缺内容、重则无法运行。先确认完整性，并找到热更缓存的落盘位置（各游戏不统一，需自行查找）。

### 三类线索

| 线索 | 内容 | 为什么重要 |
|---|---|---|
| **配置表** | 游戏数值与文本，原多为 Excel，打包成程序易读格式，大概率可逆回 Excel | 服务端数值多半在里面；缺服务端专用表时需自己填或沿用客户端值 |
| **数据包协议** | 协议的**协议号 + 传输方向 + 消息格式**汇总成的协议表 | 没有协议表，数据包就是乱码；读/生成包是重建服务端的前提 |
| **代码与热更新模块** | 热更脚本文本/中间码（Lua、TS/JS、ILRuntime/HybridCLR 等） | 业务代码多在热更模块，比汇编易读得多，AI 尤其擅长 |

引擎背景（决定改造难度）：
- **虚幻**：基本 C++ → 编译成难读汇编；（Unity）：脚本 C#，发布多走 **IL2CPP** 转 C++ → 同样难读；
- **Cocos**：TS → JS，相对可读可改，最适合"改造客户端"。

数据包要点：网游多用底层 Socket + 自研紧凑二进制协议（而非 HTTP/WebSocket，因为后者冗余大），靠**协议号**（数字或英文名）路由到对应消息格式。

### 登录架构：先分清是"直连"还是"中台"

- **直连**：登录请求由服务端直接处理——最简，按协议实现登录接口并回正确数据即可。
- **中台/SDK**：现代网游常接入统一账号平台（同一账号可登录多款游戏，角色/进度各自独立）。流程通常是：连中台 → TLS 代理转发 → 挖出回包格式 → 造假回包（账号、服务器列表、屏蔽热更）→ 客户端据回包与服务端建 Socket → 进入启动流程。

### 静态分析要产出的 5 个答案

1. 登录流程是什么？是否接入渠道 SDK / 中台？
2. 配置表在哪里？能否读出数值与内容？
3. 协议定义在哪里？能否整理出消息格式表？
4. 文件是否完整？是否有未下载的热更资源？
5. 热更新用的是什么方案？脚本/程序集在什么位置？

## 第三步：五条铁律（贯穿全程）

1. **先静态再动态、先观测后改动。** 先从文件/代码挖线索，再装日志/探针让运行态可见。没有观测就动手 = 盲修。
2. **分层拦截，自底向上。** 能改 DNS/寻址就不碰业务；能伪造协议就不改客户端。改动面最小化。
3. **一次只补一个。** 补功能一次只加一项，让改动与日志一一对应；出错时对照客户端与服务端**两侧日志**判断是格式、数据还是逻辑问题。
4. **时序即接口。** 服务端推送顺序必须匹配客户端初始化顺序：依赖某次初始化的数据，必须在触发该初始化的**请求应答之前**发出。
5. **版本门控 + 证据分级。** 每个 hook/patch 用 `模块名 + SHA-256 + 字节签名` 三重校验，不符即拒绝；每条结论标注证据级别（推断 / 静态确认 / 运行时验证）。

## 八阶段流水线

> 详细步骤、验收标准与检查清单见 `reference/playbook.md`。

| 阶段 | 目标 | 关键产出 |
|---|---|---|
| P0 静态侦察 | 文件完整性、三类线索、登录架构与传输栈、服务发现来源 | 登录架构图 + 协议/配置/热更线索清单 |
| P1 观测工具 | 注入框架 + 引擎与 VM 日志统一到文件 + 错误探针 + 崩溃兜底 | 能看到每一次登录请求/响应/异常 |
| P2 状态机建模 | 把登录全链路每一跳的 C2S/S2C/触发条件列表化 | 登录状态机草图（缺口即待探针点） |
| P3 拦截选型 | 按决策矩阵选最小改动层 | 拦截点清单 |
| P4 重定向与绕过 | 寻址→本地，TLS 处理，SDK/中台登录伪造 | 客户端流量全部落到本地 |
| P5 逐层补回包 | 从登录链最上游往下，按协议逐跳应答 | 第一个"下一步"被触发 |
| P6 时序与推送 | 补登录后同步数据、满足应答前推送 | 进入主界面 |
| P7 持续优化 | 错误驱动逐项补齐、功能验证、回归、多版本适配 | 可复现脚本 + 适配器 + 测试 |

## 决策矩阵：优先在哪一层拦？

按"改动面最小 / 通用性最高"排序，逐层尝试：

| 层 | 手段 | 何时用 | 代价 |
|---|---|---|---|
| DNS / 寻址 | 注入取地址函数，域名→`127.0.0.1`（本地同机）或电脑局域网 IP（手机连电脑） | 地址来自域名、端口可覆盖 | 最低 |
| 传输 / TLS | HTTPS 降级、阻断客户端证书校验、本地 CA、TLS 代理 | 原协议是 TLS 且无本地证书 | 中 |
| SDK / 中台 | inline hook 登录函数，伪造成功回调 | 平台登录无法离线 | 中高 |
| 业务协议 | 服务端按真实 wire format 应答 | 始终需要 | 高（但必须） |

**服务发现是重定向锚点**：定位"客户端从哪里拿到连接地址"（配置 or 登录后下发的服务器列表）。只要让下发接口返回本地地址，客户端登录逻辑通常无需改动。

## 常见坑（先看这个能省几天）

1. **热更缺失**：关服后没留热更包 → 缺内容甚至无法运行。开工前必须确认文件齐全。
2. **只信协议表**：协议表只说"消息怎么传"，**不给服务端完整实现**，缺失逻辑仍要推断与验证。
3. **ABI 不匹配**：注入 DLL 必须与目标同架构、同 STL/CRT ABI（静态 CRT 常是安全选择），否则目标进程启动即崩。
4. **改动早了**：注入要在目标初始化前拿到控制权（挂起启动 + 等目标模块加载完）。
5. **盲修 nil**：脚本 VM / 托管代码静默吞异常，必须 hook pcall / 异常分发把错误打出来。
6. **只改日志分支**：改"错误日志"≠改"判定结果"。要改在校验/判定点（如只清 `NOT_TRUSTED` 位）。
7. **时序错位**：登录后推送放在"应答之后"，客户端初始化读到空数据 → 崩溃或 UI 闪现。
8. **字段类型/引号**：JSON 里 `"0"` 与 `0` 可能走不同分支，必须按客户端解析方式对齐。
9. **无版本门控**：客户端更新后模糊 hook 随机崩溃。hash 门控 + 字节签名缺一不可。
10. **手工迭代**：没有一键起服务/注入/看日志的脚本，迭代会被拖垮。

## 交付门槛（Done 定义）

- 客户端原始文件哈希不变；
- 一键脚本可从零复现"起服务 → 重定向 → 注入 → 登录进主界面"；
- 登录闭环每一跳的消息/字段有证据分级记录；
- 关键消息有字节级或进程级集成测试；
- 差异（RVA、字段、SDK 行为）收敛为版本适配器，业务逻辑不含服别/版本判断；
- 后续功能通过"在游戏中测试 → 反馈 AI → 迭代"逐步补齐（升级数值变化、重登进度保留等功能性验证）。
