# 八阶段详细 Playbook

每阶段给出：目标 / 动作 / 验收标准 / 检查清单。可按顺序推进，也可在 P4 之后与 P5 交错迭代。

---

## P0 静态侦察（Static Recon）

**目标**：不运行游戏，先从文件与代码里把线索挖出来，并回答关键问题。

### 前提：文件完整性

- 手游安装包常只含一部分，其余靠**热更新**下载；关服后热更缓存若未留存会失传。
- 先确认客户端文件是否齐全，并定位热更缓存的落盘位置（各游戏不统一，需自行查找）。
- 后果预警：轻则缺内容，重则无法运行。

### 三类线索

1. **配置表**：先找到打包格式，尝试逆回 Excel；区分"客户端配置"与"仅服务端配置"。缺服务端专用表时自己填或沿用客户端值。
2. **数据包协议**：整理**协议表**——每条协议记录 `协议号`（数字或英文名）、`传输方向`（C2S/S2C/推送）、`消息格式`（字段号/类型/嵌套）。这是后续所有工作的基础。
3. **代码与热更新模块**：确认热更方案（Lua / TS-JS / ILRuntime / HybridCLR / 其他），定位脚本文本或中间码。热更模块里的业务逻辑最容易还原。

### 引擎背景（决定改造难度）

| 引擎 | 源码语言 | 发布后 | 改造难度 |
|---|---|---|---|
| 虚幻 | C++ | 难读汇编 | 高 |
| Unity | C# | 多经 IL2CPP 转 C++ → 难读汇编 | 高（但有热更脚本时可大幅降低） |
| Cocos | TypeScript | JS | 低，适合"改造客户端" |

### 登录架构

- **直连**：登录由服务端直接处理 → 按协议实现登录接口即可。
- **中台/SDK**：统一账号平台（一账号多游戏，角色进度独立）→ 需 TLS 代理 + 造假回包（账号、服务器列表、屏蔽热更）+ 再建 Socket。

### 要产出的 5 个答案

- [ ] 登录流程是什么？是否接入渠道 SDK / 中台？
- [ ] 配置表在哪里？能否读出数值与内容？
- [ ] 协议定义在哪里？能否整理出消息格式表？
- [ ] 文件是否完整？是否有未下载的热更资源？
- [ ] 热更新方案是什么？脚本/程序集在哪里？

**验收**：一句话说清"登录从点按钮到进主界面经过哪几段，地址从哪来"，并给出三类线索的落点。
**产出**：登录架构图 + 协议表草案 + 首包/域名清单。

## P1 观测工具（Observability First）

**目标**：在不改变行为的前提下，让登录过程完全可见。**此阶段不要做任何重定向或伪造。**

> AI 非常依赖文字日志来调试，因此把日志**完整、统一地保存到文件**极其重要。

动作：
- **注入框架**：`CREATE_SUSPENDED` 启动 → 轮询等目标模块加载 → `VirtualAllocEx` + `CreateRemoteThread(LoadLibraryW)` 加载 Payload（在目标初始化前拿到控制权）。
- **统一日志**：把**引擎日志**与**热更 VM 日志**（Lua/IL 等）统一输出到文件；所有 hook 记录 `调用者模块+RVA`、参数、返回值，按时间排序即可还原时序。
- **错误探针**：hook 脚本 VM 的 `pcall` / 托管异常分发 / CRT 的 `_purecall`/`abort`，打印被吞掉的异常与调用栈。
- **崩溃兜底**：VEH + `MiniDumpWriteDump` hook，保留真实异常上下文。
- **ABI 保障**：Payload 用静态 CRT；确认与目标同架构（x86/x64）。

验收：能完整看到一次"点击登录 → 各请求/响应 → 卡住点/报错点"。
检查清单：
- [ ] 注入成功并在目标模块加载后拿到控制权
- [ ] 引擎日志 + VM 日志统一落文件
- [ ] 每条日志含调用者定位
- [ ] 脚本/托管异常能被打印
- [ ] 崩溃有 dump/栈

## P2 状态机建模（Model Before Modifying）

**目标**：把登录链路的每一跳显式列出，缺口即未知项。

对每一跳记录四元组：`触发条件 → C2S 消息 → S2C 响应/推送 → 下一步`。

方法：
- 从客户端源码/字节码/反编译中找消息的**生产者**与**消费者**，成对列出；
- 用 grep 全量搜索消息名，未被两端都覆盖的即为未知项；
- 未知项优先装探针，不猜。

典型的登录链条（消息名按项目替换）：
```
SDK login → getServerList → getLastServerList → 选服
  → getHash(host/port/hash) → Connect(host,port)
  → player.Login → player.GetUserList → [player.CreateUser] → user.UserLogin
  → user.GetUserInfo → LoginOk → MainStage
```
检查清单：
- [ ] 每一跳有明确的下一步触发条件
- [ ] 未知项已标记并安排探针
- [ ] 区分"请求-响应"与"服务端主动推送"

## P3 拦截选型（Choose Interception Layers）

**目标**：用最小改动实现"流量到本地"。

- 默认从 DNS/寻址层开始（注入取地址函数，而非改 hosts：可进程级、可白名单、可回滚）。
- 只有必要时才上升 SDK / 业务层。
- 列出每个拦截点的：目标模块、RVA/签名、门控哈希、失败回退行为。
- 地址选择：客户端与服务端同机用 `127.0.0.1`；手机连电脑用电脑局域网 IP。

验收：先搭好一个"能监听、能记日志"的基础服务端，让客户端请求真正到达本地。
检查清单：
- [ ] 寻址重定向白名单（只改目标域名，不误伤）
- [ ] 端口可配置注入
- [ ] 每个 hook 有 hash/字节签名门控

## P4 重定向与绕过（Redirect & Bypass）

**目标**：让客户端认为"网络正常"，并把连接指向本地。

1. **寻址**：取地址函数 → 本地 IP（游戏端口），HTTP 端口单独可配。
2. **TLS 三选一**：
   - 客户端 curl 类库：hook `curl_easy_perform`，强制 TLS 版本、关校验、把 `https://` 降级为本地 `http://`；
   - 引擎自带 TLS（如 UnityTLS）：定位"校验结果判定点"，**只清 NOT_TRUSTED 位**，不要改日志/错误打印分支；
   - 最通用：本地 CA + TLS 代理，用生成的自签叶证书终止 TLS 后转发到本地 HTTP。
3. **服务发现伪造**：让服务器列表 / getHash / 配置下发接口返回本地 `host/port`。
4. **SDK/中台登录伪造**（若无法离线）：inline hook 登录函数，拦截初始化抓回调，直接伪造"登录成功"事件；必要时改引擎/框架状态标志跳过热更检查。

验收：客户端所有出网流量落到本地；登录状态机走出 SDK/中台门槛。
检查清单：
- [ ] 域名重定向日志（命中域名 → 本地 IP）
- [ ] TLS 校验处理仅在本地模式 + 校验哈希时生效
- [ ] 服务器列表返回本地 host/port
- [ ] SDK 伪造事件字段类型与真实一致（字符串/数字）

## P5 逐层补回包（Reimplement by Dependency Order）

**目标**：从登录链条最上游往下，逐跳应答；每补齐一块，以"客户端能走到下一步"为通过标准。

顺序（通用）：
1. 引导 HTTP：IP 探测、版本检查、实名、公告 —— 让客户端认为"网络正常、无需更新"；
2. 服务器列表 / 会话票据（getHash）—— 给本地地址；
3. 登录握手：建号、取角色、取用户信息；
4. 登录后同步推送 —— 主界面所需数据。

要点：
- **一次只补一个**：让每次改动与日志一一对应，便于定位；
- **两侧日志比对**：出错时同时看客户端与服务端日志，判断是"格式不对 / 数据缺失 / 逻辑没实现"；
- 严格按真实 wire format（帧头、端序、字段号/类型）；
- 每个响应记录证据来源与置信度；**协议表只说明"怎么传"，不给出服务端完整实现**，缺失逻辑需继续推断验证；
- 先让流程"能过"，再求数据完整。

验收：客户端成功发出登录后的下一条请求。
检查清单：
- [ ] 帧格式/端序与抓包一致
- [ ] 响应字段类型（引号）与客户端解析一致
- [ ] 每次只补一项，改动有对应日志
- [ ] 有字节级/进程级集成测试

## P6 时序与推送（Timing Contracts）

**目标**：进入主界面并稳定。

- 找出所有"在某个应答回调里做初始化"的位置；
- 依赖这些初始化的数据必须在该应答**之前**推送；
- 定位方法：哪个请求的 handler 触发了 `LoginOk` / 场景切换。

验收：主界面加载无致命错误；无"空数据闪现/崩溃"。
检查清单：
- [ ] 列出"应答前必须推送"的清单
- [ ] 推送顺序有回归测试

---

## P7 持续优化与泛化（Iterate & Generalize）

**目标**：从"能跑"到"能玩、可维护、可扩展、多版本可复用"。

- **错误驱动迭代**：按"跑 → 看第一个错误 → 修 → 再跑"推进，逐项清零；
- **功能验证而不只是"不报错"**：确认功能真正生效——升级后数值是否变化、重新登录后进度是否保留；
- **对照协议表 + 客户端业务逻辑**，逐步在服务端实现对应功能；
- **一键闭环**：脚本或 GUI 编排"起服务 → 生成证书 → 起代理 → 注入 → 看日志"；
- **知识库生成**：协议 / 类型 / 配置目录用工具可重复生成，不手写常量；
- **版本适配**：把 RVA 表、消息字段表、SDK 差异收敛为 `ClientAdapter`，业务代码不含版本判断；
- **门控与回归**：哈希/签名门控 + 集成测试，保证原始客户端不变。

验收：新增客户端版本主要通过"补适配器 + 补证据"完成，而非复制业务代码。
检查清单：
- [ ] 功能有"生效"验证（数值/持久化），不只无报错
- [ ] 一键脚本可从零复现
- [ ] 登录闭环文档含证据分级
- [ ] 适配器与业务逻辑解耦
- [ ] 原始客户端哈希不变
